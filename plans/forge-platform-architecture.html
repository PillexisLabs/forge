The words, in plain terms

Read this box first. Every term used on this page, explained the way you'd explain it over chai.

Module
A self-contained feature block — like an appliance you plug into a house. WhatsApp automation is one appliance, voice calling is another. Unplug one and the house still works. Each module owns its own screens, tables, and code in one folder.
Core
The plumbing and wiring of the house. Login, the one shared list of leads and conversations, logging. Every module plugs into core; no module works without it.
Event / event bus
A shared notice board. When something happens, a module pins a note: "lead replied". Other modules read the board and react. Modules never talk to each other directly — only through notes on the board. That is why removing a module breaks nothing.
Manifest
The label on the appliance box. One small file per module that says: its name, its version, what settings it needs, and which notes it pins to and reads from the board. Want to know what a module touches? Read the label, not the code.
Provider adapter
A universal travel plug. The module speaks one plug shape ("send a message"); the adapter converts it for whichever outside service the client uses — Meta, Twilio, Exotel. Swap the service, keep the module.
Upstream
Our master copy of core and all the modules — the one Forge repo we keep improving forever. Every client project starts as a copy of this.
Client copy
A photocopy of upstream, handed to a client on day 1 in their own GitHub. They own it fully — no lock-in. From that moment their copy and our original change independently.
Foundry / scaffolding
The photocopy machine. A command that picks the modules a client bought, prints a complete copy, and pushes it to their GitHub. It also writes forge.lock — the receipt that records which module versions their copy was printed from.
Demo workspace
A showroom. A separate running copy of Forge filled with fake businesses and a reset button, used live on sales calls. Nothing in it is real client data.

The big picture: three layers

One repo. Core is the foundation everything shares. Modules are the sellable capabilities. Foundry stamps out client copies.

Layer 1 · Forge Core — src/core/
The shared foundation
Mostly exists today in src/lib/. Every module plugs into this. It holds the one copy of the truth: who the lead is, and what happened.
Data spine
One set of tables: contacts, leads, conversations. Modules extend these. No module makes its own copy of "a lead".

What one module looks like inside

Every module follows the same folder shape, so anyone on the team can open any module and know where things live.

Anatomy — example: WhatsApp
src/modules/whatsapp/ ├── manifest.ts name, version, config it needs, events in / out ├── migrations/ its own tables, prefixed: wa_flows, wa_messages ├── api/ webhook + API routes, mounted by core ├── ui/ its screens, mounted under /m/whatsapp ├── workers/ crons and queue consumers └── providers/ adapter over Meta / Twilio — swappable per client
RULE 1
No cross-imports
Modules talk only through core events and the shared lead tables. Never import from another module.
RULE 2
Providers are adapters
Every outside service sits behind an interface. Swap Exotel for Twilio without touching module logic.
RULE 3
No Pillexis values in module code
Client identity lives only in config. If a module hardcodes anything Pillexis-specific, it cannot be copied out.

A module gets a new feature — who is affected?

Short answer: usually nobody. Modules cannot import each other's code, so a change inside one module has no path to reach another. The only two shared surfaces are the notice board (events) and the core tables. A feature only matters to others when it touches one of those two — and this table is the complete list of what's safe and what's not.

Type of changeEffect on other modulesRule
New screens, tables, or logic inside a module none Ship it. Nobody else can see it.
Pin a new kind of note to the board (new event) none Safe. Modules ignore notes they don't know. Add it to the catalog.
Add a field to an existing note (event payload) none Safe, as long as it's additive. Readers skip fields they don't use.
Rename or remove a note, or change what a field means breaks readers silently Never. Ship lead.qualified.v2 next to the old one, move readers over, then retire v1.
Change a core table (leads, contacts, conversations) touches everyone Only core migrations may do this, add-columns-only, reviewed against every module's manifest.

The manifest makes this checkable in seconds: every module's label declares which notes it pins and reads. Before merging, one search over the labels answers "who reads this note?" — you know the blast radius before shipping, not after.

Avoiding duplicates: four kinds, four rules

"Don't repeat yourself" means something different for data, code, features, and client copies. Each has its own rule.

DATA
One list of leads, ever
Core owns leads, contacts, conversations. A module never makes its own copy — its tables point at core IDs (wa_messages.lead_id → leads.id). A PR adding a table that smells like "leads again" gets rejected.
CODE
Needed by two? It moves to core
Shared helpers (phone formatting, retries, logging) live in core. A lint rule physically blocks one module importing from another — so the only way to share code is to move it to core. Copy-paste between modules is the one door that's locked.
FEATURES
Every capability has one owner
The voice module never sends a WhatsApp message. If a call should trigger a follow-up text, voice pins a note — followup.requested — and the WhatsApp module, the owner of sending messages, handles it. Two modules never build the same thing.
CLIENT COPIES
Duplication here is the product
Each client owning a full copy IS the business model. The dedupe point is upstream: improvements flow client → upstream → future clients. Never sideways from one client's repo to another's.

WHY TWO VENDORS
Each does one job
Twilio only carries the call (the phone line). Sarvam only handles speech (ears, brain, mouth). Both sit behind adapters — a client on Exotel or English-only ElevenLabs is a config change, not a rewrite.
THE ECONOMICS
~₹10 per qualified call
500 calls/month ≈ ₹5,000 of usage. The same volume on ElevenLabs ≈ ₹19–28k, on OpenAI Realtime ≈ ₹14–24k. Sarvam is beta pricing — even doubled, this stack wins 3–4x.
THE REAL RISK
Latency, not money
The spike's pass/fail test: hear → think → speak in under 1.2 seconds per turn. If the pause feels robotic, the demo dies regardless of cost.
COMPLIANCE
Consent before dialing
TRAI/DND rules apply to automated calls. We only call leads who consented in the WhatsApp step — consent capture is built into that flow, and the worker checks it before every dial.

Forward flow · upstream → client
"Diff and port"
Their photocopy was taken in January (forge.lock says WhatsApp 1.2). By June our original is at 1.5. Diff = list what changed in the original since their copy was taken. Port = carry over only the changes they want, test in their setup, open a PR on their repo. Usually happens on the next paid engagement; a security fix is offered right away.
# inside the CLIENT's repo
git remote add upstream git@github.com:PillexisLabs/forge.git
git fetch upstream

# the diff: what changed in this module since their cut
git log --oneline upstream/master -- src/modules/whatsapp/

# the port: carry over only the commits they want
git cherry-pick <commit1> <commit2>
Reverse flow · client → upstream
"Strip and land"
We built something for one client that every future client will want. Strip = a review pass that removes everything client-specific: hardcoded prices become config, their keys and copy text are deleted. Land = PR into upstream, bump the module version, add a changelog line. The client keeps their original — nothing is taken, only generalized.
# inside OUR upstream forge repo
git remote add humpy git@github.com:humpyfarms/forge.git
git fetch humpy

git checkout -b port/subscription-flows
git cherry-pick <feature-commit-1> <feature-commit-2>

# strip: hardcoded values → config, client bits deleted
git commit -am "Generalize subscription flows"
# land: PR → master, bump module version + changelog
WHY CHERRY-PICK WORKS
Same file paths, different histories
The two repos share no git history, but the scaffolder keeps the folder tree identical — so commits apply cleanly across them. Conflicts resolve like any merge.
FALLBACKS
When cherry-pick is awkward
Patch files (git format-patch → git am) need no repo access — a client can email a .patch. Or plain folder copy + read the diff: loses history, fine for small changes.
BEST WORKAROUND
Avoid reverse flow entirely
Spot mid-project that a feature is generic? Build it in upstream first, then forward-port it to the client immediately. Reverse flow is then only for surprises.
DELIBERATELY REJECTED
No npm packages, no submodules
Private packages or submodules would give automatic updates — but the client's repo would then depend on infrastructure we control. That is exactly the lock-in we sell against. Manual ports are the honest price of true ownership.

Deliberately not building

Half the value of this plan is what it avoids.

No multi-tenancyOne deployment = one client. The internal Pillexis analytics instance is just workspace #1.
No public signup or billingForge is a delivery backbone and a demo, not a SaaS product.
No forced updates to client reposClients own their copy. Improvements travel forward on the next engagement, not by pushing into their repo.
No module marketplaceFour modules, done well, matched to what the corpus says people ask for.
Why this matters commercially
Modules give you a fixed-price SKU sheet. About half the pipeline cannot afford ₹80k/month but asks for plug-and-play. "WhatsApp lead qualification, fixed price, live in two weeks" is the offer that converts them — and the demo workspace is how you sell it in the call itself.
