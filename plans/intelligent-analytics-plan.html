02System architecture

Sync path stays the same. New layer: the intelligence stack sitting between raw data and the human.

Everything above Postgres already exists. Everything below the accent line is new: typed rules, per-ad diagnostic, and the AI copilot that turns firing rules into a ranked brief. The copilot writes back to insights_history so we can measure it.

04The insight schema

The one non-negotiable rule from memory: every insight must carry all six fields. If it can't, it's not an insight — it's a chart.

Rules fire on Postgres rows. Output is a typed Insight. The typed object is what flows to UI cards, the morning brief, the chat agent's context, and insights_history for outcome tracking. One shape, every surface.

05Creative diagnostic funnel

Per-ad, four checkpoints. The lowest-scoring level is the weakest link. Gemini looks at that level's creative and says why.

Each level scored as a percentile vs account. Weakest level (here: Persuasion, P28) is what Gemini gets. The card then quantifies: "move Persuasion from P28 to P50 → +12 Schedules/wk at current spend."

06The AI agent — Ad Ops Copilot

One agent, three modes. Reads the same typed insights the UI reads. Writes only through guarded, confirmed tools.

Reads are open. Writes are guarded — always confirmation-modal, always logged with source: agent. The agent is not autonomous. It's an operator that drafts and Anurag ships.

Why this specific agent shape

not a chatbot bolted on
The agent reads the same typed insights the UI reads. No parallel truth. If the rule says X, the agent explains X — never invents a new diagnosis.
not autonomous
Zero unconfirmed writes. Every action passes through a confirm modal. Meta ads_management scope stays local. This is a copilot, not autopilot.
closes the loop
Every agent-executed action writes to insights_history with source: agent. Phase 5's ΔCPL join then proves whether the agent's advice moved the number.
two models, cost-aware
Haiku 4.5 for the daily brief (fast, cheap, deterministic-ish). Opus for chat where reasoning matters. Gemini for vision because you already paid for the key.

07Native app or web app?

You already have both surfaces in the stack. The question is which one earns a new build.

verdict
Web (stay on Next.js). Deliver the morning brief through Forge or email. No new native surface.
The dashboard, chat, action tools, and outcome tracking all fit inside the existing Next.js app running on localhost:3000. Building a parallel native app is duplicated work with zero user reachable outside Anurag. Forge already solves the "morning notification on macOS" problem — extend Forge to render one extra card ("Ad Ops brief") instead of shipping a second native shell.
Web app · pros
  • Existing sync, DB, insights, launchd all reusable
  • Chat panel + /ads route drop straight into Next.js
  • Charts, tables, Gemini image previews render better than in native
  • Zero App Store, code signing, Sparkle-updater overhead
  • Multi-tenant future (see Meta Business Partner path) needs web anyway
Native app · when to reconsider
  • If iOS morning brief becomes the primary surface (unlikely — Anurag's on Mac)
  • If you need OS-level notifications with actions (Forge already handles this)
  • If you sell to founders who won't install Node/Docker (multi-tenant → SaaS solves this instead)
  • If Meta App Review demands a specific desktop bundle (they don't — web ok)

Concrete recommendation: ship Phase 6 as three surfaces on the web app — the /ads route, the chat panel on /, and a signed morning brief endpoint that emails plain HTML at 07:05. If you later want a native card, add one screen to Forge that fetches the same endpoint. No parallel product.
